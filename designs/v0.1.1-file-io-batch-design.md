# RadiChat v0.1.1 File I/O and Batch Support

## Intent

Add small, reproducible file-based configuration and batch I/O to RadiChat. This serves local batch testing and non-interactive container Jobs while preserving RadiChat as a single-process OpenAI-compatible terminal client. Existing line-oriented stdin behavior remains the baseline.

## Goals

- Load a system prompt from a UTF-8 file with clear validation and context-budget checks before any request.
- Keep stdin redirection and its sequential, one-line-per-turn semantics.
- Add `-input PATH` for environments where a process has no usable stdin, such as the current shell-free container image.
- Add explicit JSONL results through `-output PATH` or JSONL-only stdout through `-output -`.
- Document a non-interactive Kubernetes Job example without adding Kubernetes application code.
- Use only the Go standard library and retain existing inference protocol behavior.

## Non-goals and anti-goals

No persistence or session reload, database, retries, concurrent requests, scheduling, orchestration, Kubernetes API client, Helm/operator, new dependency, protocol change, image build/publication, or product fixes unrelated to this milestone. Do not report partial streamed text as a successful result. Do not mix progress or diagnostics into stdout in JSONL stdout mode. Do not overwrite an existing JSONL output file.

## Approaches

1. **Extend the existing REPL with dedicated I/O components (selected).** Keep the REPL responsible for sequencing conversation operations. A dedicated input component owns bounded line reading and numbering; a dedicated JSONL writer owns encoding and output errors. Conversation staging, commit, abort, clear, and trimming remain in existing conversation/client paths. This preserves behavior without mixing file I/O into conversation state.
2. **Build a separate batch runner.** This would isolate result formatting but duplicate line, command, and error semantics. It is likely to drift from the REPL and is not selected.

## Interfaces and behavior

### System prompt file

Add optional `system_prompt_file` to configuration. It must be a non-empty JSON string and conflicts with `system_prompt` whenever both keys are present, including an empty inline value. Relative prompt paths resolve against the lexical `filepath.Dir` of the config path as given; absolute paths are used directly. `Load` follows symlinks, requires a regular file, caps it at the existing 1 MiB file limit, validates UTF-8, strips one leading UTF-8 BOM and exactly one final LF or CRLF, and rejects an empty result. It reads once at startup. Errors identify the path and problem but never include prompt bytes.

Apply the existing context-fit policy at startup to either an inline or file-sourced non-empty system prompt, checking that the system message, an empty user message, and generation reserve fit. This makes validation consistent between the two prompt sources. Configurations with no system prompt, including an empty inline string, keep existing behavior. Failure occurs before any endpoint request. The fit check stays outside `internal/chat`; `chat.Fits` is called during startup.

### Input and output components

The command line becomes `radichat [-config PATH] [-input PATH] [-output PATH|-]`. `main` opens the input and output paths before the REPL and passes only an `io.Reader` and a record-writer interface; the REPL never receives paths. The input component owns bounded line reading, physical line numbering, blank-line detection, and overlong-line detection. `config.Parse` stays pure; `config.Load` reads prompt files. `internal/chat` gains no file I/O.

`-input PATH` is relative to the current working directory and always non-interactive. It preserves existing line limits, CR handling, blank-line behavior, `/clear`, `/quit`, EOF, and per-turn failure behavior. The path is opened before the REPL; a missing path or directory exits 1 without a request. Regular files and FIFOs are accepted; opening a FIFO waits for its writer. With no new flags, stdin output remains byte-identical to current behavior except for the Owner-approved startup fit check for non-empty system prompts and SIGTERM handling. There is no `-input -` or JSONL input. Interactive input remains allowed with `-output`. A file literally named `-` is passed as `./-`.

Startup validation order is: load config and prompt, run prompt fit checks, open and validate input, then create requested JSONL output last. Thus a missing input, invalid prompt, or failed fit check never leaves a new output file behind. `-output PATH` creates a new file exclusively with mode `0600`; if it already exists, startup fails without a request and without changing it. It never appends or overwrites. Existing terminal streaming remains on stdout. `-output -` sends JSONL only to stdout, suppresses streamed assistant deltas and their trailing newlines, and keeps diagnostics on stderr; every byte written to stdout in this mode belongs to a JSONL record. The dedicated writer encodes each record as one JSON line without HTML escaping and performs one write per record. A record-write failure exits 1 immediately and prevents subsequent requests. A broken stdout pipe retains Go/Unix default SIGPIPE behavior (typically shell status 141).

### JSONL v1

Each non-blank physical input line produces one record when handled. Blank lines (including whitespace-only lines according to existing trimming rules) produce none; line numbers are 1-based physical positions including blanks. For turn input, `input` is the line after existing CR removal. For command errors, `input` is the raw line after CR removal and before whitespace trimming. Records have `v` (JSON integer 1), `line` (positive JSON integer), and `kind` (JSON string). Only fields listed below are present; absent fields are omitted, never `null`.

| `kind` | `status` | Additional fields and JSON types |
| --- | --- | --- |
| `turn` | `ok` | `input` string, `output` string, `finish_reason` string (`stop`, `length`, or empty), `trimmed_pairs` integer |
| `turn` | `error` | `sent` boolean, optional `input` string (omitted for an overlong line), `error` string |
| `turn` | `interrupted` | `sent` boolean, `input` string; no `output` or `error` |
| `clear` | absent | no additional fields |
| `quit` | absent | no additional fields |
| `command_error` | absent | `input` string, `error` string |

Representative records:

```json
{"v":1,"line":3,"kind":"turn","status":"ok","input":"hello","output":"hi","finish_reason":"stop","trimmed_pairs":0}
{"v":1,"line":4,"kind":"turn","status":"error","sent":true,"input":"again","error":"endpoint returned HTTP 500"}
{"v":1,"line":5,"kind":"turn","status":"error","sent":false,"error":"line too long"}
{"v":1,"line":6,"kind":"turn","status":"interrupted","sent":true,"input":"continue"}
{"v":1,"line":7,"kind":"clear"}
{"v":1,"line":8,"kind":"quit"}
{"v":1,"line":9,"kind":"command_error","input":" /unknown ","error":"unknown command"}
```

The `/quit` record is written before input stops. No records are written for lines after `/quit`, a record-write failure, or interruption. An interruption while waiting for a new input line has no input line to correlate and produces no record. An in-flight turn interrupted by SIGINT/SIGTERM gets a best-effort `interrupted` record; if that record fails to write, the signal exit code still takes precedence. Consumers must ignore an incomplete final line after SIGKILL. No timestamps or latency fields are included.

Stream failures abort staged conversation state as they do today, are recorded, and do not prevent later input lines from being handled; the process retains the existing final nonzero-on-any-turn-failure behavior. `/clear` retains the system prompt. `/quit` stops input. A final line without a newline is processed. The input BOM behavior remains unchanged. SIGINT continues to exit 130 (apart from the optional best-effort JSONL interruption record for an in-flight turn); SIGTERM exits 143. An interruption exit code takes precedence over exit 1 from earlier failed turns. JSONL records contain prompts and responses; file output is private (`0600`) and opt-in.

### Kubernetes documentation

Add JSON-format Kubernetes Job and ConfigMap examples (Kubernetes accepts JSON manifests) using mounted configuration, prompt, and input files; `-input` and `-output -`; no stdin/TTY; read-only root filesystem; non-root user; dropped capabilities; no privilege escalation; `restartPolicy: Never`; `backoffLimit: 0`; and an active deadline. JSON allows structural validation with the Go standard library, avoiding a YAML dependency. Cross-check ConfigMap keys against Job args/mounts, ensure the prompt resolves under `/config`, parse the embedded `radichat.json` with the real config parser, and assert the image value contains `REPLACE_WITH_V0_1_1_DIGEST`. The endpoint is cluster DNS and optional bearer-token configuration references a Secret, never a ConfigMap. The JSON files are the tested manifest source; docs may show the unescaped config separately for readability. Validate with `encoding/json` and required-field assertions; do not claim a real cluster run. Explain that `kubectl logs` can interleave stdout and stderr, so JSONL consumers must separate or filter the streams.

## Scope and validation boundary

Expected code touchpoints include config loading, CLI startup, the existing REPL coordinator, dedicated input and JSONL writer components, and an additive client result/API for finish reason metadata so accepted client behavior remains compatible. Documentation covers `PROJECT.md` Capabilities, CLI/configuration, batch JSONL, Kubernetes usage, context accounting, and the README. A durable decision records path/output rules and the startup fit check as an extension of decision 0001. No `.factory/` files are product source. No Kubernetes code is added.

Validation covers prompt source parity and invalid files, startup fit failure with zero requests, symlink and size/UTF-8 boundaries, batch record count and line correlation, success/error/partial-stream rollback, JSON escaping and omission of absent fields, clear/quit/unknown command, EOF without final newline, auth redaction, no-overwrite and missing-input/directory startup failures, output-created-last behavior when startup fails, JSONL-only stdout, `/dev/full` write failure stopping further requests with exit 1, real SIGTERM interruption/143, read-only working-directory use, stdin byte compatibility except the approved system-prompt fit and SIGTERM changes, Kubernetes JSON cross-file/config validation, and repository checks (`gofmt`, `go test ./...`, `go test -race ./...`, `go vet ./...`, `go build ./...`, help smoke check, and public-surface check). No real Kubernetes cluster or image execution is claimed.
